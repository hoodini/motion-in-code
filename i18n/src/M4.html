המוזיקה היא השעון: BPM, ביטים, דרופ וסאונד לפי שיא

"Something happens on every beat" — ואיך מחשב "שומע" את הביט.

BPM (Beats Per Minute) = כמה פעימות בדקה. 120 BPM = ‏2 פעימות בשנייה = ביט כל 0.5 שנייה. תיבה (bar) = 4 ביטים. דאונביט = הביט הראשון בתיבה, החזק. דרופ = הרגע שבו אחרי בנייה כל הכלים נכנסים בבת אחת — שיא האנרגיה.

ברגע שיודעים את ה-BPM, כל תכנון הסרטון הופך לטבלה: ביט 0 — זה קורה, ביט 1 — זה. בגלל זה הפרומפטים מדברים בביטים ולא בשניות. בדקתי את המספרים שלו — הם מדויקים:

מחשבון ביטים

איך numpy "שומע" את הקצב — שלב אחרי שלב

הפרומפט אומר "Analyze it with numpy and give me the beat grid". מה קורה מתחת לפני השטח (אני מריץ כאן בדפדפן בדיוק את האלגוריתם הזה, על שיר שמסונתז עכשיו):

  1. מה זה קובץ שמע: רשימה ארוכה של מספרים בין ‎−1 ל-1 — מיקום הממברנה של הרמקול. 22,050 מספרים לכל שנייה.
  2. מעטפת אנרגיה: חותכים לחלונות של 256 דגימות (~12 מילישניות) ומחשבים בכל חלון RMS (שורש ממוצע הריבועים) = "כמה חזק" בחלון.
  3. Onset ("התחלת צליל"): לכל חלון — בכמה הוא חזק יותר מהקודם (רק עליות). תוף שמכה = קפיצה חדה. זה הופך את השיר לרשימת "דפיקות".
  4. אוטוקורלציה: מזיזים את רשימת הדפיקות על עצמה בהיסטים שונים ובודקים מתי היא הכי "מתלכדת" עם עצמה. אם יש דפיקה כל 0.5 שנייה, ההיסט של 0.5 שנייה נותן את ההתאמה הכי גבוהה → 120 BPM. (מעדיפים קצב קרוב ל-120 כי אחרת האלגוריתם עלול לבחור חצי או כפול.)
  5. פאזה: יודעים כל כמה, צריך לדעת מתי — מחפשים את ההיסט ההתחלתי שבו הרשת נוחתת על הכי הרבה דפיקות.
  6. הדרופ: מחשבים אנרגיה ממוצעת לכל ביט ומחפשים את הביט עם הקפיצה הגדולה ביותר ביחס לשני הביטים שלפניו.
זיהוי ביטים ודרופ — אמיתי, על שיר מסונתז
מגבלה אמיתיתעל שיר אמיתי זיהוי אוטומטי טועה לפעמים (חצי-קצב, דרופ מזויף). לכן בפרומפט ה-footage שלו כתוב "Calibrate the grid to the real kick hits" — לכייל את הרשת למכות התוף האמיתיות, ובסקיל הפתוח של Howseen כתוב במפורש "never trust an auto beat grid". הלקח: הרשת היא היפותזה שבודקים, לא אמת.

אפקט סאונד "לפי השיא הנמדד" — הפרט הקטן שעושה את ההבדל

בפרומפט: "Place each so its measured peak, not its file start, lands on the event." לקובץ של "ווש" יש התחלה שקטה שעולה עד שיא — הרגע שהאוזן שומעת כ"הנה!". בקובץ שלנו השיא נמצא 0.42 שנייה מתחילת הקובץ. אם מנגנים את הקובץ ברגע הדרופ, השיא מגיע 0.42 שנייה אחרי הדרופ — כמעט ביט שלם באיחור, והאוזן מרגישה שמשהו "לא נוחת". הפתרון: למדוד איפה השיא, ולהתחיל את הקובץ ב-זמן האירוע − זמן השיא.

ווש על ביט: לפי תחילת קובץ מול לפי שיא
הגדרה: loudnorm ל-‎-14 LUFSLUFS היא יחידה למדידת עוצמה כפי שאוזן אנושית שומעת אותה (לא סתם שיא הגל). loudnorm הוא פילטר של ffmpeg שמביא את כל הסרטון לעוצמה נמדדת קבועה. ‎−14 LUFS הוא יעד נפוץ לפלטפורמות סטרימינג — כך הסרטון לא יישמע חלש מכל השאר בפיד, וגם לא "יוחלש" אוטומטית.

מושן בלר מתת-פריימים: למה 4 משאיר "רוחות רפאים" ו-8 לא

"8 subframes per frame blended with ffmpeg tmix" — כל מילה, כל מספר.

הבעיה: מצלמה אמיתית פותחת את התריס לפרק זמן (למשל חצי מזמן הפריים — "תריס 180°"). מה שזז בזמן הזה נמרח בתמונה. זה ה"מושן בלר", והמוח רגיל אליו כל כך שבלעדיו תנועה מהירה נראית "מגמגמת" ומלאכותית. אבל צילום מסך של דפדפן הוא רגע אחד אינסופית קצר — אפס מריחה.

הפתרון: לכל פריים סופי, מצלמים N "תת-פריימים" בזמנים צפופים בתוך חלון התריס, ומחשבים ממוצע פיקסל-פיקסל. ממוצע של 8 מיקומים קרובים של עיגול = עיגול מרוח. ffmpeg tmix הוא בדיוק פילטר שממצע N פריימים רצופים.

למה 4 לא מספיק בתנועה מהירה: המרחק בין שני תת-פריימים הוא מהירות × זמן תריס ÷ N. אם המרחק הזה גדול מהאובייקט עצמו — העותקים לא נוגעים זה בזה, ורואים 4 עותקים שקופים נפרדים: "ghost copies". הפרומפט אומר "use 8 and slow the move down" — שתי הדרכים להקטין את אותו מספר.

מעבדת מושן בלר — ממוצע אמיתי של תת-פריימים

ופקודת ה-ffmpeg — בדקתי אותה בפועל לפני שכתבתי אותה כאן: יצרתי 24 תת-פריימים מלאכותיים ווידאתי שכל פריים יוצא הוא הממוצע של 8 התת-פריימים שלו ולא מערבב שכנים:

verified: each output frame = mean of its own 8 subframes
# 60 fps × 8 subframes = 480 images per second of film
ffmpeg -framerate 480 -i sub_%06d.png \
  -vf "tmix=frames=8,select='eq(mod(n\,8)\,7)',setpts=N/(60*TB)" \
  -r 60 -c:v libx264 -pix_fmt yuv420p -crf 16 video.mp4

tmix=frames=8 ממצע כל פריים עם 7 שלפניו. select='eq(mod(n,8),7)' שומר רק כל פריים שמיני — את זה שהממוצע שלו מכסה בדיוק קבוצה שלמה. setpts מסדר מחדש את חותמות הזמן ל-60fps. גוטצ'ה מהסקיל של Howseen: לעולם לא ממצעים על פני חיתוך קשה — אחרת שתי סצנות נמרחות זו לתוך זו.

"It checks its own work": בקרת איכות שקלוד עושה לבד

החוק השביעי — והסיבה שהתוצאה לא נראית כמו "פרומפט אחד ותקווה".

כל פרומפט שלו נגמר ב-<start> שמחייב: לפני כתיבת הסרט המלא — מפת ביטים ו-4 סטילס לאישור. ואחרי הרינדור — שתי בדיקות: פריים אחד לכל ביט, וסריקת "pops".

בדיקה 1: גיליון מגע — פריים אחד לכל ביט

זה בדיוק מה שקלוד "מסתכל" עליו. הנה הגיליון של הסרטון מלמעלה, מחושב עכשיו מאותה seek(t) — פריים בכל חצי שנייה:

Contact sheet: 18 ביטים בתמונה אחת

בדיקה 2: סריקת "pops" — תקלה של פריים אחד

Pop = פריים בודד שבו משהו קופץ למקום לא נכון ומיד חוזר (שכבה שהופיעה מוקדם, משתנה שלא הוגדר). ב-60fps העין קולטת את זה כ"הבהוב" מעצבן, אבל קשה מאוד למצוא אותו בצפייה. האלגוריתם: לכל זוג פריימים רצופים מחשבים הפרש ממוצע בין הפיקסלים. בתנועה חלקה ההפרש משתנה לאט. Pop יוצר זינוק — פי 3 ויותר מהשכנים — בדיוק כמו שכתוב בפרומפט: "frame-difference spikes 3x their neighbours".

סורק pops — מזריקים תקלה ומחפשים אותה
למה זה קריטי דווקא ל-AIמודל שכותב קוד ארוך עושה טעויות קטנות (z-index שנשכח, משתנה שלא אותחל לפני ה-seek הראשון — שתיהן מופיעות ב-gotchas שלו). בדיקות מספריות הופכות "אני חושב שזה טוב" ל"מדדתי, אין זינוקים". זה בדיוק ההבדל בין דמו ויראלי לבין משהו שאפשר למסור ללקוח.

import { chromium } from 'playwright';
const FPS = 60, SUB = 8, SHUTTER = 0.5, DUR = 9;      // seconds
const browser = await chromium.launch({ args: ['--use-angle=d3d11', '--enable-gpu', '--ignore-gpu-blocklist'] });
const page = await browser.newPage({ viewport: { width: 1920, height: 1080 } });
await page.goto('http://localhost:8000/film.html');
await page.evaluate(() => document.fonts.ready);       // never shoot before fonts load
let i = 0;
for (let f = 0; f < DUR * FPS; f++) {
  for (let k = 0; k < SUB; k++) {                       // subframes spread across the shutter
    const t = f / FPS + (SHUTTER / FPS) * ((k + 0.5) / SUB - 0.5);
    await page.evaluate(t => window.seek(t), t);         // may be async (images, video)
    await page.screenshot({ path: `out/sub_${String(i++).padStart(6, '0')}.png` });
  }
}
await browser.close();
מחשבון עלות רינדור

המספרים בכפתורים לקוחים מהרינדורים האמיתיים שלנו בפרויקט: בסביבת הענן (CPU בלבד) הגענו לכ-7 פריימים בשנייה; על ה-RTX 4090 שלך, 7 workers במקביל, כ-6 לשנייה כל אחד. תת-פריימים מכפילים את העבודה — לכן בטיוטות מרנדרים בלי מושן בלר וברזולוציה נמוכה, ומושן בלר רק במאסטר.
