Under the hood: WebGL, WebGPU and shaders

Who actually paints the pixels, and why it matters when we capture a film.

In the previous chapter three.js did the work for us. Now we go one layer down, to two questions: who actually draws, and in which language we talk to it.

  • Graphics card (GPU): a processor made of thousands of small cores that do the same operation on lots of data at once. The regular processor (CPU) is a few expert chefs; the graphics card is a thousand cooks who each chop one cucumber. Drawing an image is exactly that kind of work: millions of pixels, and the same calculation for each one.
  • WebGL: the browser's long-standing way to talk to the graphics card, since 2011 (and version 2 since 2017). It works in almost every browser and device, and three.js uses it by default.
  • WebGPU: the new way. Faster when there are many objects, and it can also do general computing (compute): using the graphics card not only for drawing but for any calculation that repeats, like a simulation of hundreds of thousands of particles. According to Google (November 2025) it is available in Chrome and Edge (on Windows, macOS, ChromeOS and Android), in Safari 26, and in Firefox on Windows and on Macs with ARM chips. On Linux it is still on its way, and that matters to us, because render machines usually run Linux.
  • Shader: a small program that runs on the graphics card. A fragment shader runs once for every pixel in every frame and returns a colour. A vertex shader runs once for every point of a shape and decides where it appears on screen. In WebGL shaders are written in GLSL, in WebGPU in WGSL.
  • TSL (Three Shading Language): three.js's shader language. We write it as ordinary JavaScript, and it turns into WGSL or GLSL by itself, depending on what the browser supports.

Why does this matter for a film? Because a shader is exactly a function of time: colour = f(pixel, t). It is the same idea as seek(t), except the graphics card runs it on a million pixels at once. A sunset, a sea, marble and film grain are a few lines of code, with no image file at all.

The video-render trapWhen Playwright captures the film, it runs the browser headless: with no window, usually on a server. In that mode Chrome turns the graphics card off by default. WebGL keeps working through SwiftShader, software that imitates a graphics card on the regular processor: slower, but it works and comes out the same every time. WebGPU needs special flags, and on some servers drivers too. We tested it: with the flags --enable-unsafe-webgpu --enable-features=Vulkan --use-vulkan=swiftshader --use-webgpu-adapter=swiftshader the WebGPU demo below runs even without a graphics card. Without the flags, three.js falls back to WebGL 2 by itself.

How to choose an engine, in four lines

  1. Interface, buttons and text: HTML and CSS. The browser already draws them very well.
  2. Illustrations, charts and 2D motion: Canvas 2D, a drawing surface we paint on with commands.
  3. 3D, materials and shaders: three.js with WebGLRenderer. The safe choice for rendering.
  4. Hundreds of thousands of particles or a simulation: three.js with WebGPURenderer, which falls back to WebGL 2 by itself when there is no WebGPU.
06.1

Shader: a colour for every pixel

WebGL 2GLSLno library

What you see

Five worlds drawn without a single image and without a library: a sunset, a sea, marble, a liquid gradient and paper with grain. Each one is a single function a few lines long. Open "The code that paints every pixel" to see it, and pick a world with the buttons.

How it works

  • The canvas is covered by one triangle bigger than the screen. The graphics card runs the shader once for every pixel the triangle covers, which means the whole canvas, all in parallel.
  • Every pixel gets its position (p) and the time (t) and returns a colour. There is no memory between frames, so any frame can be computed on its own, exactly like seek(t).
  • Marble and paper are made of noise: a function that returns random numbers that change gradually, like a landscape of hills rather than TV static. We add a few layers of noise at different sizes (fbm) and bend one noise with another (domain warping), and marble veins appear.
  • The grain in the gradient and the paper is not decoration: a smooth gradient breaks into colour "steps" after video compression (banding), and fine noise hides it.
When to useBackgrounds, skies, water, textures and atmosphere, with no heavy files and full quality at any resolution.
When not toAn object with a defined shape (a phone, a bottle). There, three.js with a model is better.

Build textures from value noise and fbm (4 to 5 octaves); use domain warping for marble-like veins; add grain as hash(pixel + floor(t * 24)) at about 3% amplitude.

</build>

<gotchas>
- smoothstep(edge0, edge1, x) with edge0 > edge1 is undefined in GLSL. Write 1.0 - smoothstep(a, b, x) instead.
- Waves near the horizon get so dense that they flicker (aliasing). Fade their amplitude to zero near the horizon.
- Headless Chrome has no GPU by default; WebGL still runs through SwiftShader, only slower. Keep the shader cheap (loops of 5 steps at most).
- Use highp precision, or noise turns blocky on some mobile GPUs.
</gotchas>

06.2

WebGPU: two hundred thousand particles

three.jsWebGPURendererTSL

What you see

200,000 particles that move from a sphere to a galaxy to a wave. The corner shows what your browser is actually running: WebGPU, or WebGL 2 when it has no WebGPU.

How it works

  • three.js comes in two versions: three with WebGLRenderer, and three/webgpu with WebGPURenderer. The second tries WebGPU and, if it is missing, falls back to WebGL 2 by itself. That takes a moment, so we wait for await renderer.init() before the first frame.
  • All the particles are copies of the same small square (instancing): the graphics card gets one shape and a number of copies, and draws them all in one command.
  • Each particle's position is computed on the graphics card, in TSL: from the particle's index we derive three fixed random numbers, from those three shapes, and one number that comes from t decides how far we are from one shape to the next. Each particle starts a little after its neighbour, which turns the morph into a wave.
  • WebGPU's great strength is general computing (compute), such as a simulation in which every frame is built from the previous one. In a film we prefer a pure function of t, so we can jump to any frame, which is why everything here is recomputed every frame directly from t.
When to useA "wow" moment of sheer quantity, morphing between shapes, a logo built from particles.
When not toParticles as decoration on a black background. That is exactly the "template" zero bans.

- WebGPURenderer does not support ShaderMaterial or onBeforeCompile; write custom shading in TSL.

- Additive blending of 200,000 particles blows out to white. Keep each particle's colour around 25% brightness.
- Import everything in this file from 'three/webgpu'; mixing it with 'three' loads two copies of the library.
</gotchas>
